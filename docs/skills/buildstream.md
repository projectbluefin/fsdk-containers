# BuildStream Reference

## Overview

The **syntax and mechanics cheat sheet** for `.bst` authoring in this repo. It is not
the end-to-end workflow for adding an image — that is
[add-new-image.md](add-new-image.md).

Adapted from `projectbluefin/dakota`'s `docs/skills/buildstream.md`. Dakota builds a
bootable OS from `gnome-build-meta`; this repo builds distroless OCI images from FSDK
`components/*`. The BuildStream mechanics are shared; the targets and hard rules are not.
**Dakota-only patterns that must NOT be copied here:** composing from `platform.bst`,
and `x86_64_v3` — both are banned by [AGENTS.md](../../AGENTS.md).

## When to Use

- Choosing an element kind or source kind
- Getting install paths and variables right
- Remembering directive syntax (`(@)`, `(?)`, `(>)`, `(<)`)
- Validating or inspecting the element graph

## When NOT to Use

- Adding a whole new image end-to-end → [add-new-image.md](add-new-image.md)
- A build is failing → [bst-debugging.md](bst-debugging.md)
- Junction refs, overrides, or the patch queue → [bst-junctions.md](bst-junctions.md)
- Making an image smaller → [slim-an-image.md](slim-an-image.md)

## Core Process

1. **Validate the graph before building.** `bst show` is orders of magnitude cheaper
   than `bst build` and catches every YAML and graph error.
2. **Choose the element kind that matches the real build model** — not the one you
   used last time.
3. **Use standard variables and `%{install-root}`** for install paths.
4. **Prefer existing repo patterns over invention.** Copy `elements/python/` and
   `elements/oci/python.bst` before writing anything from scratch.
5. **Inspect a single element** before escalating to a full image build.

## Project facts (this repo)

Verified against `project.conf`, `Justfile`, and `include/`:

- `min-version: 2.5` — BuildStream 2.5 directives and features are available.
- `element-path: elements`.
- One arch option, values `aarch64` and `x86_64`. **No `x86_64_v3`** — this is a
  broad-compatibility baseline, and re-adding v3 is banned.
- `variables:` derives `go-arch` (`amd64`/`arm64`) from `arch` via a `(?)` block;
  `elements/oci/*.bst` consume it as `%{go-arch}`.
- Source aliases live in `include/aliases.yml` and are pulled in with `(@)`:
  `pypi`, `github`, `gitlab`, `gnome`, `k8s-bin`.
- `include/fsdk-version.yml` is **generated by the `just bst` wrapper on every
  invocation** and is gitignored. It is not a hand-maintained file — never edit it,
  and never treat it as a second source of truth for the FSDK version. The single
  source of truth is the `ref:` in `elements/freedesktop-sdk.bst`.
- Plugins come from junctions: `git_repo` and `patch_queue` from
  `plugins/buildstream-plugins-community.bst`; the `collect_initial_scripts`
  element from `gnome-build-meta.bst`.

## Quick Recipes

BuildStream runs inside the FSDK `bst2` container via the `just bst` wrapper. Local and
agent builds are submitted to the ghost cluster's BuildBarn grid by default; `BST_LOCAL=1`
is the explicit opt-out. See [remote-execution.md](remote-execution.md).

| Goal | Command |
|---|---|
| Validate the whole graph | `just validate` |
| Resolve one element | `just bst show oci/<name>.bst` |
| Inspect a stack/runtime element | `just bst show <name>/<name>-runtime.bst` |
| Build one element | `just bst build oci/<name>.bst` |
| Enter the build sandbox | `just bst shell --build <name>/<name>-runtime.bst` |
| Track a source ref | `just bst source track <element>` |
| List built contents | `just bst artifact list-contents <element>` |
| Read the build log | `just bst artifact log <element>` |
| Drop a cached (or cached-failed) artifact | `just bst artifact delete <element>` |
| Build + load the default image | `just build` |
| Run the merge contract | `just verify` |

When passing `--format` to `just bst show`, **avoid spaces** — the Justfile recipe
word-splits its arguments. Use a separator like `%{name}--%{state}`.

## Element Kinds

| Kind | Use case | Used here for |
|---|---|---|
| `stack` | dependency aggregation only; **produces no filesystem output** | `<name>/<name>-stack.bst` |
| `compose` | filesystem-producing layer/filter step; applies `exclude:` domains | `<name>/<name>-runtime.bst` |
| `script` | image assembly — stages deps, runs commands, calls `build-oci` | `elements/oci/<name>.bst` |
| `manual` | custom build/install, pre-built binaries | tool elements |
| `import` | direct file placement, no build | file payloads |
| `make` / `meson` / `autotools` / `cmake` | matching upstream build system | source builds |
| `junction` | external project boundary | `elements/freedesktop-sdk.bst` |

`stack` vs `compose` is the single most common mistake: a `stack` aggregates
dependencies and emits **nothing** to the filesystem. If you expect files, you need
`compose`.

## The three-element pattern

Every OCI image in this repo is the same shape (see
[add-new-image.md](add-new-image.md) for the full procedure):

```
elements/<name>/<name>-stack.bst      kind: stack    — FSDK component deps + base stack
elements/<name>/<name>-runtime.bst    kind: compose  — chisel via exclude: domains
elements/oci/<name>.bst               kind: script   — SLIM recipe, prune, build-oci
```

## Source Kinds

| Source kind | Use case |
|---|---|
| `git_repo` | most source trees (`ref-format: git-describe` is set project-wide) |
| `tar` | release tarballs — use `base-dir: ""` if there is no wrapping directory |
| `remote` | a single downloaded file |
| `local` | repo-local files |
| `patch_queue` | patch application — see [bst-junctions.md](bst-junctions.md) |
| `go_module` | Go module dependencies (community plugin) |
| `cargo2` | Rust crate vendoring (community plugin) |

**Source URLs do not expand `%{variables}`.** Use an alias from
`include/aliases.yml` instead (`github:owner/repo.git`).

## Key Variables

| Variable | Expands to | Notes |
|---|---|---|
| `%{install-root}` | staging dir | **prefix every install path with it** |
| `%{prefix}` | `/usr` | FSDK is merged-usr |
| `%{bindir}` | `/usr/bin` | binaries go here, not `/usr/sbin` |
| `%{indep-libdir}` | `/usr/lib` | arch-independent lib data |
| `%{datadir}` | `/usr/share` | data files |
| `%{sysconfdir}` | `/etc` | use sparingly |
| `%{install-extra}` | trailing hook | convention: end `install-commands` with it |
| `%{go-arch}` | `amd64` / `arm64` | repo-defined; used in `build-oci` blocks |
| `strip-binaries` | set to `""` to disable | **required for non-ELF payloads** |

## Directive Syntax

| Syntax | Meaning |
|---|---|
| `(@):` | include YAML from another file |
| `(?):` | conditional block, keyed on project options |
| `(>):` | **append** to an inherited list |
| `(<):` | **prepend** to an inherited list |

`(@)` composites at any mapping level, and the **including file wins** on conflict.
This repo already uses it for `include/aliases.yml` (in `project.conf`) and
`include/slim.yml` (under an element's `variables:`), which is the pattern to copy
when factoring shared commands out of elements.

**Option names may only contain alphanumerics and underscores.** A hyphenated name
like `my-option` is invalid — use `my_option`. This trips up agents copying names
from CLI flags.

## Overlaps

When your element installs a file that an FSDK junction component also provides,
BuildStream raises an overlap error at compose time. Declare a whitelist in the
authoring element:

```yaml
public:
  bst:
    overlap-whitelist:
    - /etc/some/file    # literal path, not a %{variable}
```

**A whitelist is not precedence.** It only silences the error — the file that
survives is decided by **staging order**, and your element can lose to a junction
element. To make the winner deterministic, add a runtime `depends:` on the component
that ships the original so yours stages after it, or do the overwrite in a later
phase. Then assert the result on the composed image, because a silent flip is
otherwise invisible. This shipped as a real regression in dakota (zram config
whitelisted but overwritten by the junction, dakota#1131).

## Remote-sandbox constraints

Builds run on BuildBarn workers, not on your machine. Two patterns that work
locally and fail remotely:

- **Never use `/dev/stdin` redirection.** `install -Dm644 /dev/stdin ... <<'EOF'`
  fails in sandboxes that do not mount `/proc`. Write inline files in two steps:
  `install -Dm644 /dev/null <target>` then `cat > <target> <<'EOF'`. Heredocs
  themselves are fine; only the `/dev/stdin` indirection breaks. This regressed in
  dakota across nine element sites after the lesson was first written (dakota#1298)
  — check for it in review.
- **Go builds need an explicit `GOROOT`.** The FSDK Go toolchain installs its
  standard library under `%{libdir}/go`, and dependent elements do not inherit
  `GOROOT_BOOTSTRAP`. Set `GOROOT: "%{libdir}/go"` in any element invoking
  `go build`, or remote actions fail with `go: cannot find GOROOT directory`.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "`stack` and `compose` are basically the same." | No. `stack` aggregates deps and produces no filesystem output. |
| "I'll validate by building — same difference." | `bst show` catches graph/YAML errors in seconds instead of minutes. |
| "Variables should expand in source URLs too." | They do not. Use an alias. |
| "This binary probably goes in `/usr/sbin`." | FSDK is merged-usr. Default to `%{bindir}`. |
| "`compose exclude: shells` removes bash." | It does not. Bash is in the `runtime` domain. The SLIM recipe `rm`s it explicitly. |
| "It built on my machine, so it will build in CI." | Local and CI may not use the same sandbox. See remote-sandbox constraints. |

## Red Flags

- `kind: stack` where filesystem output is expected
- source URLs with fake `%{variable}` expansion
- install paths without a `%{install-root}` prefix, or outside `/usr`
- `/dev/stdin` heredoc redirection
- hyphens in option names
- reaching for a full image build to diagnose a YAML error
- composing from `platform.bst`, or any reintroduction of `x86_64_v3`

## Verification

- [ ] The element kind matches the real build/input model
- [ ] `just validate` resolves the graph cleanly
- [ ] Install paths use standard variables and merged-usr locations
- [ ] Any filesystem-producing layer is `compose`, not `stack`
- [ ] No `/dev/stdin`, no hyphenated options, no URL variable expansion
- [ ] `just verify` still passes for every image you touched
